# AB-021 · Ciclo de vida do computador browser

`BrowserComputerService` usa o contexto Docker selecionado pelo caller, sem alterar configuração global. Cria uma box identificada por UUID estável e terminal UUID em labels próprios, com imagem `racky-browser:ab019-dev`, volume nomeado exclusivo `/data`, porta do container 8765 publicada em `127.0.0.1` com porta efêmera, CPU/memória da política efetiva, PID e shm limitados, capabilities removidas, `no-new-privileges`, root filesystem read-only e tmpfs de home pertencente ao UID 10001. O serviço exige rede permitida e limite efetivo de pelo menos 2048 MiB, em vez de exceder a política silenciosamente. O mesmo lock e teto de capacidade contam computadores HTTP e browser; restart revalida política e estado running. Apenas containers com labels/nome próprios são iniciados ou parados.

O bearer `AB_API_TOKEN` é aleatório por computador, guardado no Keychain com namespace separado dos segredos do usuário e entregue ao Docker por env-file temporário `0600`, removido após `docker create`. Metadados duráveis contêm somente IDs, container e volume, nunca o token. O administrador do daemon Docker ainda pode ver variáveis do container via inspect; o Keychain protege os metadados do app em repouso, não é uma fronteira contra administradores Docker.

`reconnectEndpoint` descobre e valida exclusivamente uma porta `127.0.0.1`, usa sessão efêmera sem redirects para consultar `/v1/health` autenticado, verifica UUID e geração, e só então devolve um `BrowserRuntimeEndpoint`. O modo inicial HTTP é saudável mesmo com `browser_ready=false`; a prontidão de desktop é validada separadamente pelo viewer. Metadados perdidos podem ser reconstruídos das labels de containers próprios, mas registros conflitantes são recusados. `BrowserComputerStore` expõe estado e endpoints em memória, cria/inicia/para de forma explícita e aguarda até 4 segundos pela prontidão inicial. A UI de configuração/painel existente ainda precisa ser ligada a este store pelo integrador.

`BrowserComputerServiceTests` usa runner e Keychain falsos: confere flags, publicação local, volume, limpeza do env-file, metadados, health de identidade, stop e rejeição da política desativada. Core typecheck isolado passou. O integrador executa o conjunto Swift serialmente e o runtime agent validou a imagem arm64 real com os flags hardened listados.
