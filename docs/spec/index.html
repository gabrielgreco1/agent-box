01 · Contrato do produto

Objetivo: transformar o protótipo v0.4 e o skill Agent Box em um aplicativo pessoal de macOS para organizar sessões com vários terminais reais, preservar os harnesses de Claude Code, Codex e OpenCode e entregar computadores Docker opcionais aos agentes que trabalham nesses terminais. O foco inicial é pesquisa, coleta e validação de dados, com intervenção humana na mesma sessão de navegador.

Esta é a especificação de referência para a próxima implementação. Consolida as correções de 16 de outubro de 2026 e substitui as decisões conflitantes da spec v0.4: sessão deixa de significar um terminal; desktop deixa de ser obrigatório; o centro da interface passa a ser uma área de terminais divididos. “DEVE” indica requisito; “proposto” indica escolha técnica inicial ainda sujeita à prova descrita neste documento.

  • Sessão → terminais → execuções de agentes/subagentes → computadores opcionais. A biblioteca de agentes é independente dessa árvore.
  • A conversa é a TUI original do CLI em PTY. Nenhum compositor de chat próprio ou loop LLM substitui o harness.
  • O cliente CLI roda no Mac; ferramentas de trabalho podem executar na box. Containers Linux compartilham o runtime Docker do Mac: não são uma VM completa dedicada a cada agente.
  • O principal de cada terminal decide delegação e necessidade de computador, dentro da política do usuário. A sessão do app é um agrupamento, não um agente orquestrador adicional.
  • Todo recurso exibido na versão operacional vem de estado observado. Ausente, desconhecido, reconectando e não suportado são estados reais; não usar fixtures como fallback silencioso.
  • A nova direção visual usa densidade, árvore, abas e painéis semelhantes ao Orca, com marca própria e logos oficiais dos provedores. Não reutilizar conteúdo dos projetos pessoais observados no Orca.

Escopo e limites

Entram no produto: shell avulso, pasta comum, Git/worktree, descoberta e retomada suportada de conversas, múltiplos PTYs, árvore de subagentes, capacidades por versão, Docker adaptativo, streaming/takeover, listeners, perfis, credenciais, configurações iniciais, biblioteca de agentes/skills, memória explícita, evidência e exportação. Sem billing, marketplace, publicação SaaS, colaboração multiusuário ou runtime remoto nesta primeira versão.

Troca de modelo dentro do mesmo harness é distinta de transferência Claude↔Codex↔OpenCode. Não prometer contexto interno portável, subagente com terminal próprio quando não há PTY, retomada exata após crash, captura universal de rede ou desbloqueio de um site apenas por abrir interface gráfica. Os testes de capacidade decidem quais controles ficam habilitados.

O modelo suporta árvores de subagentes; a UI abre apenas os níveis relevantes e oferece breadcrumb para árvores profundas. Nomes são rótulos, não identidade. Dois “Pesquisador” simultâneos nunca compartilham recursos por coincidência de nome. Relações e eventos usam IDs estáveis; um terminal tem no máximo um processo foreground controlador por geração. A mesma conversa nativa não pode ser retomada em dois terminais de escrita sem suporte explícito do provedor.

O layout guarda uma árvore de splits com orientação, proporção e folhas terminal_id. Redimensionar, recolher sidebar, maximizar pane ou mudar abas não recria PTY. Uma aba pode conter um grupo de panes; um terminal não aparece duas vezes com input independente no mesmo layout. Encerrar terminal não apaga sessão, worktree, perfil ou histórico.

Quando cinco panes não couberem legivelmente, manter alguns em abas ou maximizar o focado; não reduzir fonte automaticamente para caber tudo.

  • Logos vêm dos arquivos oficiais existentes. Agente pessoal pode ter avatar escolhido, mas não ganha uma marca de provedor falsa. Fallback é nome e ícone funcional.

06 · PTYs, sessões nativas, Git e CLIs

Decisão: usar um emulador de terminal nativo, com SwiftTerm como candidato já pesquisado, encapsulado atrás de TerminalRenderer. O pacote preparatório fixa 1.20.0; a integração deve validar essa versão e o lockfile antes de adotá-la. PTYHost vive no serviço local, não dentro do ciclo de vida de uma View. SwiftUI administra panes; AppKit integra foco, seleção, clipboard, menus e acessibilidade. Não usar LocalProcessTerminalView com processo pertencente à view e ao mesmo tempo prometer sobrevivência ao fechamento do app sem um host persistente separado.

  1. Resolver executável por configuração explícita e PATH do usuário, sem assumir PATH de um app lançado pelo Finder. Probe de versão/status tem timeout e não roda na main thread.
  2. Abrir processo com argv, cwd e ambiente filtrado. Shell login é uma escolha documentada; não interpolar pasta, prompt, segredo ou branch num comando de shell.
  3. Criar PTY com tamanho inicial correto, TERM e UTF-8; propagar resize/SIGWINCH. Suportar ANSI, 256/truecolor, alternate screen, bracketed paste, Unicode, scrollback e TUIs interativas.
  4. Manter ring buffer com limite configurável e política de retenção. Conteúdo de terminal não é audit log seguro; captura persistente é opcional e tem tratamento próprio de sensibilidade.
  5. Fechar pane somente remove visualização se o terminal continua em outra aba. Encerrar terminal sinaliza o grupo de processos correto; timeout oferece encerramento forçado explícito. Nunca matar processos por nome global.
  6. Ao desconectar/reconectar UI, reanexar pelo PTY ID e geração. Não executar de novo comando inicial nem reenviar input sem ACK. Se o serviço morrer, reconhecer perda do processo e oferecer retomada nativa quando suportada.

Separar Descobertas no CLI, Abertas neste app e Arquivadas. Usar API/comando público por preferência; importação de metadados locais deve ser leitura limitada e versionada, sem varrer conversas inteiras ou arquivos de credenciais. Git e GitHub

Pasta comum e avulso são caminhos de primeira classe. Quando há Git, mostrar branch do checkout efetivo de cada terminal, dirty state e remote normalizado sem credenciais embutidas. A sessão mostra “Várias branches” quando necessário. Worktree é opt-in: validar repositório/ref, branch existente, destino vazio, caminhos e rollback de criação incompleta. Não fazer stash/reset/clean automático nem remover worktree ao fechar um terminal.

Integração GitHub começa read-only: identificar remote GitHub, consultar autenticação existente da integração escolhida, mostrar link do repositório e PR quando resolvido. Remote presente não significa conta conectada. Criar branch, push, PR ou merge são ações separadas; nenhuma ocorre ao abrir ou renomear sessão. Repositórios não GitHub continuam funcionando.

07 · Delegação e computador por subagente

A skill ensina quando solicitar computador, como delegar e como pedir ajuda. MCP fornece ferramentas. O adaptador observa a identidade e o ciclo de vida do harness. O serviço aplica autorização, capacidade e associação. Nenhuma dessas peças substitui o loop original do Claude Code, Codex ou OpenCode.

  1. O terminal inicia com namespace da sessão, ID do terminal e conexão da integração. Configuração fica escopada ao lançamento/projeto; não sobrescrever defaults globais silenciosamente.
  2. O agente principal solicita trabalho delegado usando mecanismo nativo. Eventos verificáveis registram filhos e suas relações; uma linha de texto na TUI nunca concede autoridade.
  3. O principal pode reservar capacidade para filhos ainda não criados; reserva não é um vínculo ativo e expira. Alternativamente, o filho pede computador após sua identidade ser reconhecida.
  4. computer.request inclui intenção, modo solicitado, perfil autorizado e idempotency_key. O serviço deriva o ator da conexão/adaptador, verifica política e faz reserva atômica.
  5. A capacidade concedida é vinculada a run_id, computer_id e epoch. Repetir request após timeout retorna a mesma concessão; não cria outro container.
  6. Fim de subagente registra resultado, revoga controle e aplica política de parada. Um pedido de ajuda pendente não é descartado sem resolução.

O Claude Code documenta hooks SubagentStart/SubagentStop com agent_id e conexões MCP escopadas ou compartilhadas. Isso ajuda a registrar filhos, mas não prova sozinho a identidade de cada chamada de ferramenta. Hooks · MCP por subagente. Codex documenta threads de subagentes e MCP; a propagação de identidade até a chamada exige um spike específico. Subagentes Codex. OpenCode também tem agentes primary/subagent, mas seus eventos precisam da mesma prova. Agentes OpenCode.

Gate obrigatório de identidade

Testar dois filhos do mesmo tipo em paralelo. Se o adaptador não conseguir autenticar qual deles fez a chamada, não oferecer exclusividade por filho nessa integração. Exibir “Identidade por subagente indisponível nesta versão” e permitir computador do principal ou um worker em CLI independente explicitamente identificado como tal. O principal pode receber capacidades delegáveis, mas o serviço precisa limitar destinatário e escopo; um box_id fornecido pelo modelo não autoriza acesso.

No host, CLIs com shell irrestrito executam como o usuário e podem alcançar arquivos/serviços acessíveis a esse usuário. A política do broker não cria uma sandbox macOS automaticamente. A implementação deve distinguir “controlado pelo broker” de isolamento efetivo. Para prometer takeover/exclusividade, os caminhos que escrevem no computador devem passar pelo controle dentro da box; não distribuir socket Docker nem CDP de escrita irrestrito aos agentes. Scripts executados na box também precisam ser pausáveis ou restritos durante controle humano. Um pipeline que deixa esses caminhos livres não passa o gate de controle.

Instalação e recursos

Detectar runtime existente e sua arquitetura. Docker Desktop, Colima ou outro compatível devem passar pelo mesmo adapter de health; a escolha final depende de teste local, não de um nome fixo na UI. Instalação, downloads e termos exigidos são visíveis no setup. A permissão “agentes podem criar computadores” é distinta de instalar dependências e de liberar diretórios do host. A licença de um runtime não deve ser aceita por uma caixa de permissão genérica.

Proposta inicial para benchmark no Mac observado de 24 GiB: duas boxes de navegador simultâneas e teto agregado conservador configurável; não assumir que dez browsers cabem porque dez subagentes foram solicitados. Preflight mede memória/disco disponíveis e explica a fila. Definir limites de CPU/memória/PIDs, shared memory para browser, disco/capturas e concorrência por sessão. Limite global vence limites locais. Aumentar modo exige reserva de recursos antes de iniciar o componente. Limites Docker.

Imagem ARM64 fixada por digest, dependências versionadas e health por componente. Começar com uma imagem que comporte os três modos, inicializando componentes sob demanda; só separar imagens por economia de disco/startup após medir. Para cada computer_id, manter gerações de container e referências a volumes. Não incluir logins na imagem. Runtime supervisado com sinais, encerramento ordenado e logs de diagnóstico sanitizados. Escalonamento headless → desktop

  1. Receber motivo e conferir política, recursos e necessidade de intervenção. Um 429 pede espera; erro TLS pede diagnóstico; abrir GUI não é mecanismo universal de desbloqueio.
  2. Marcar transitioning e impedir novas ações daquele executor. Drenar/cancelar ações em voo; resultado incerto deve ser reconciliado antes de repetir.
  3. Persistir progresso da tarefa, filas, URLs, artefatos e estado recuperável do browser. Encerrar browser de forma limpa e obter lock exclusivo do perfil.
  4. Iniciar display, navegador headed compatível e transporte. Reaproveitar perfil autorizado. A troca de modo pode reiniciar processo e perder estado volátil; nenhuma garantia de DOM/formulário/socket em memória idêntico.
  5. Checar health, página, autenticação e cobertura do listener. Se falhar, manter checkpoint e erro explícito; restaurar modo anterior apenas se operação for segura.
  6. Publicar nova geração/epoch, invalidar comandos antigos e então disponibilizar stream ou pedido de ajuda.

O Playwright configura headless no lançamento e permite perfil persistente, com exclusividade de diretório. Portanto a primeira implementação trata a mudança como transição recuperável, não troca instantânea do processo em execução. BrowserType. Se a tarefa exige takeover sem perder estado volátil, iniciar headed desde o começo e suspender somente transmissão quando ninguém observa. Desligar streaming não é o mesmo que virar headless.

HTTP não compartilha automaticamente cookies com o navegador. Qualquer importação/exportação de estado entre cliente HTTP e browser precisa ser específica, autorizada por perfil e testada. Depois de intervenção, manter headed até um ponto seguro; não reiniciar a cada troca de foco. Uma política de inatividade e histerese evita alternância contínua.

09 · Streaming, ajuda e controle exclusivo

O viewer é uma superfície do app e recebe stream apenas do computer_id selecionado. Proposta de transporte para a primeira prova: noVNC em WKWebView, isolado atrás de RemoteDesktopView; validar renderer nativo depois conforme custo/benefício. A UI, terminais e configurações permanecem nativos. Streaming e input usam ticket de curta duração, sem segredo na URL/log. Viewer deve distinguir conectado, atrasado, reconectando e erro.

agent → quiescing → human → reconciling → agent
                     ↘ disconnected / suspended
  1. ask_user cria request_id, motivo (login/verificação/download/escolha), run_id, computer_id e contexto sanitizado. O pedido aparece no filho, terminal e sessão por agregação; há um som por request_id, não por reconexão.
  2. Assumir solicita mudança de posse. O serviço revoga concessão do agente, incrementa epoch e para caminhos de escrita, inclusive subprocessos controlados. Espera ACK antes de habilitar mouse e teclado do usuário.
  3. Enquanto human, irmãos com outras boxes continuam. Ações antigas são rejeitadas e novas ações automatizadas aguardam; captura sensível pode ser suspensa pelo modo privado.
  4. Devolver encerra input humano, reconcilia URL/abas/arquivos/downloads e devolve um resumo de estado ao executor. Não enviar senha, token ou conteúdo privado do login.
  5. Se stream cair durante takeover, desabilitar input e suspender controle. Reconectar não resolve automaticamente o pedido nem autoriza o agente a agir.

Fechar o viewer não fecha a box. Abrir fullscreen não muda dono. Clipboard e upload/download são capacidades independentes e escopadas; user input não vira automaticamente memória do agente. Notificação do macOS é solicitada no momento apropriado, e falha de permissão mantém alerta interno. Suporte de acessibilidade de pixels remotos é limitado e não equivale à árvore VoiceOver de uma app local.

Previews por hover são read-only, nunca transferem foco nem controle. HTTP mostra eventos; headless mostra captura com horário; desktop mostra thumbnail em frequência reduzida. Orçamento proposto: um stream focado, até duas thumbnails ativas; demais por demanda. Meta inicial de input local p95 abaixo de 200 ms e feedback de UI abaixo de 100 ms, medidos no hardware alvo; não resultados já obtidos.

13 · Agentes salvos, memória, modelos e handoff

AgentDefinition guarda nome, descrição, instruções, origem, hash e revisão. SkillRevision referencia instruções/recursos com compatibilidade por cliente. Importar é leitura/validação; executar instalação ou hooks de uma definição é ação distinta. OpenCode, Claude e Codex têm formatos e capacidades diferentes: converter somente o que o adapter entende e apresentar campos não suportados. Não carregar todos os agentes/skills em todo terminal.

AgentRun registra revisão da definição, skills e memórias selecionadas, native_session_id/native_agent_id, modelo confirmado e capabilities. AI memory distingue preferência do usuário, conhecimento do projeto, tarefa, perfil e histórico de execução. Cada entrada tem fonte, escopo, autor, created/updated, validade, estado e revisão. O usuário pode editar, excluir da seleção ou arquivar. Resultados de sites permanecem evidência e não se tornam instrução confiável.

Histórico de agente mostra sessões, terminais, computadores, perfis utilizados, resultados e revisões. “Usar novamente” escolhe nova tarefa ou retomada; não garante que o processo anterior será ressuscitado. Memória ligada a um perfil não atravessa identidades automaticamente. Cookies e segredos ficam fora do contexto textual.

Biblioteca no estilo do Maestrum

A biblioteca é uma área permanente, independente das sessões. Lista compacta com busca, favoritos e filtros por compatibilidade. Ao selecionar um agente, abrir abas Instruções, Memória, Skills e Histórico. Mostrar quais sessões/terminais o usaram, computadores e perfis associados, tarefas realizadas e revisão que efetivamente rodou. Não confundir uma definição salva com um subagente vivo.

  1. Criar agente: nome, descrição, instruções editáveis, CLI/modelo preferidos opcionais, skills padrão, política de memória e recursos permitidos. Salvar não inicia uma execução.
  2. Editar/duplicar/arquivar: nova revisão preserva históricos existentes. Execuções em andamento continuam na revisão antiga; aplicar mudanças exige nova execução ou operação suportada pelo cliente.
  3. Usar agente: escolher sessão e terminal, nova tarefa ou retomada, revisar memória e skills selecionadas e lançar no harness original. A definição não ganha computador automaticamente.
  4. Promover execução a agente salvo: oferecer apenas instruções e memória revisadas; não importar segredos, transcrição inteira ou conteúdo de páginas como regras confiáveis.

Memória revisável e reutilizável

Cada memória tem título, conteúdo, tipo, escopo, origem/evidência, revisão e validade opcional. Tipos: preferência, conhecimento verificado, procedimento e nota de tarefa. Criar, editar, pesquisar, selecionar, arquivar e excluir são ações reais e persistentes. Sugestões produzidas pelo agente entram numa fila de revisão; não são promovidas automaticamente a instruções globais. A UI mostra o contexto que será entregue antes do lançamento e permite remover itens individualmente. Limite de contexto e resumo preservam links para a fonte; não truncar silenciosamente. Excluir memória impede reutilização futura, mas não apaga o que já foi enviado a um CLI; histórico registra somente referências/revisões permitidas.

Catálogo e ativação de skills

Skills têm nome, descrição, caminho/origem, versão/hash e compatibilidade por harness. Importar arquivo/pasta local e descobrir diretórios explicitamente autorizados; não instalar ou executar por simples seleção. Visualizar SKILL.md e recursos referenciados antes de ativar. Ativação padrão na definição pode ser ajustada por execução; mostrar de onde veio cada seleção. Skill removida/incompatível bloqueia ou exige retirar explicitamente a seleção, nunca desaparece do contexto sem aviso. Definições e skills nativas continuam nos formatos do CLI quando possível; o adapter injeta somente através de mecanismos suportados, sem substituir o harness.

A primeira versão pode entregar edição local, persistência e exportação de contexto antes de adapters de ativação nativa. Nessa etapa, “salvo” e “disponível para exportação” não significam “ativado no Claude/Codex”. A UI deve distinguir esses estados. Memória, skills e histórico têm critérios próprios e não são decoração do layout.

Modelo versus harness

Seletor de modelo trabalha no terminal/execução selecionado, não em estado global. Uma mudança no principal não altera filhos já ativos silenciosamente. Catálogo e mecanismo vêm do adapter; mostrar pending até confirmação. Não digitar /model em um terminal arbitrário durante edição, comando ou prompt de aprovação. Sem API segura de mudança, abrir o controle nativo do CLI ou orientar seleção ali; preservar a escolha inicial no lançamento.

Trocar Claude↔Codex↔OpenCode cria conversa no harness de destino ou retoma uma compatível. Fluxo: verificar destino/auth/capabilities → pausar operações → checkpoint explícito → revogar concessões de escrita → iniciar destino → associar recursos → validar retomada → marcar transferência concluída. Falha conserva checkpoint e permite retornar ao cliente anterior. Filhos ativos bloqueiam a troca ou são encerrados/aguardados conforme escolha explícita; não migrar árvore em execução por suposição.

Checkpoint inclui objetivo, critérios, decisões do usuário, próximos passos, artefatos, linhas do dataset, evidências, estado observável da box e referências permitidas de memória. Exclui raciocínio privado, credenciais e histórico indiscriminado. A UI responde imediatamente ao pedido, mas duração operacional depende de pausa e retomada; não prometer troca instantânea entre harnesses.

Confiabilidade e fronteiras

Ações internas sobre Docker ficam atrás de comandos tipados; agentes recebem ferramentas com capacidades, não controle arbitrário do daemon. Montagens explícitas, processo não root onde compatível, rede e portas mínimas e sem modo privileged por conveniência. Docker pode compartilhar diretórios do host, portanto autoridade sobre seu daemon é ampla; a arquitetura deve limitar esse acesso. Docker Engine security. Isolamento de containers não restringe por si só um CLI local com shell irrestrito.

O gate decisivo usa uma sessão com dois terminais reais, dois subagentes identificados e duas boxes. Um inicia HTTP, outro headless; o segundo passa a desktop e solicita ajuda. O humano assume, o primeiro continua, os dados persistem e a UI reanexa. Só depois ampliar para cinco terminais e dez subagentes, com fila de recursos. Documentar por cliente o que foi comprovado; “o browser abriu” não prova identidade, isolamento ou continuidade.

Entregas por PR/local change devem ter escopo revisável, migração reversível e nenhum dado pessoal em fixtures. Testar mudanças de runtime com processos e sites próprios; não usar conversas ativas do Orca para executar comandos de teste. Manter o protótipo anterior arquivado como referência e não promover imagens fictícias a evidência de funcionamento.

Critérios para considerar o produto utilizável

  • Tarefas do fluxo diário executadas nos CLIs originais, com estados reais e sem etapas simuladas na rota principal.
  • Sessões, layout, definições, resultados e perfis sobrevivem ao ciclo de vida previsto; falhas têm recuperação explícita.
  • Takeover e vínculos por agente comprovados com testes de concorrência e negação de acesso.
  • Configuração de recursos/segredos é compreensível e aplicada na fronteira técnica correspondente.
  • Checklist AC completo com versão, data e evidência; exceções documentadas e controles indisponíveis de forma honesta.
